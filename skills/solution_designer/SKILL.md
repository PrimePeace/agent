# 技术方案

默认只在下面两种里选，并写清为什么不选另一种。没有新证据时不要发明第三种架构。

## 选型规则

| 信号 | 选择 |
| --- | --- |
| 峰值未知，或低于 2000 QPS | 模块化单体 |
| 峰值达到或超过 2000 QPS | 按业务能力拆分的微服务 |
| 已有独立团队长期拥有该能力 | 可以提前拆出该能力 |
| 只是「以后可能会大」 | 仍选单体，等出现真实扩容指标再拆 |

## 模块化单体

一个可部署单元，内部分成接口、领域和存储模块。一致性靠单库本地事务，不引入两阶段提交。复杂度低：一条流水线、一套数据库、一个值班对象。扩容以垂直为主，读路径可加缓存。

## 按业务能力拆分的微服务

每个服务一个库，服务之间不共享数据库。跨服务只传递已提交的事件，用发件箱：业务数据和事件写在同一个本地事务里，再异步投递，失败可重试。代价是要处理超时、重复投递和跨服务排障，每多一个服务就多一份发布、监控和值班成本。

## 对比必须有的四列

复杂度、性能、成本、可维护性。推荐理由必须指回原文的峰值、一致性或团队约束，不要写「业界通常这样做」。

## 一致性的三种写法

- 原文要求强一致或没写：单体用本地事务；微服务内部本地事务，跨服务用发件箱。
- 原文接受最终一致：本地写成功后异步通知其他读模型。
- 任何情况都不要推荐两阶段提交和分布式事务框架。

## 退回

清晰度低于 60 时退回问题梳理一次。同一方向只退回一次，第二次拿到仍不完美的简报就用冻结的假设继续，把疑问写进 residualRisks。
