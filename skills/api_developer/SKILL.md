# 接口契约

一个业务名词对应一组资源。调用方和资源分开：「用户可以创建订单」里资源是订单，路径是 `/api/orders`，不是 `/api/users`。

## 标准端点


| 方法   | 路径                      | 用途            | 状态码             |
| ---- | ----------------------- | ------------- | --------------- |
| POST | /api/sessions           | 登录建立会话（需要认证时） | 201 / 401       |
| GET  | /api/{slug}             | 分页列表          | 200             |
| POST | /api/{slug}             | 创建            | 201 / 409 / 400 |
| GET  | /api/{slug}/{id}        | 按标识读取         | 200 / 404       |
| POST | /api/{slug}/{id}/cancel | 取消（原文提到才加）    | 200 / 409       |


取消用 POST 子资源而不用 DELETE，因为取消是业务动作，有自己的规则和响应体。

## 幂等

每个 POST 都要求 `Idempotency-Key` 请求头：

- 同一个键、同一份正文：返回第一次的结果，状态码也相同。
- 同一个键、不同正文：返回 409，说明键被占用。
- 键的保存期至少覆盖调用方的重试窗口，例如 24 小时。

服务端实现：以幂等键为唯一索引先插记录，冲突时读旧结果返回。不要用「先查再插」，并发下会重复。

## 分页

用 limit 加 cursor。cursor 是上一页最后一条的排序键编码，不是页码。不要用大 offset，会被跳页放大成全表扫描。

## 错误响应

统一结构：`{"code": "ORDER-4009", "message": "幂等键已被另一笔请求占用"}`。状态码表达协议结果，错误码表达业务原因。沿用后端角色的错误码表；没有后端产物时也要区分 400、401、404、409、500。

- 响应体里有没有内部字段（版本号可以有，堆栈、SQL 不可以）？
