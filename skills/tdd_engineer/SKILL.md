# 测试

顺序固定为红、绿、重构：先写一条会失败的测试，再写刚好让它通过的生产代码，然后去掉重复、保持绿色。不要先写完实现再补测试，那样测试只会复述实现。

## 从验收标准到用例

把问题简报里的每条验收标准翻成一条测试，命名讲清场景和期望，例如 `duplicate_idempotency_key_returns_first_result`。断言状态码和错误码，不断言文案——文案会改，业务含义不会。

必备用例：

- 创建成功后立刻按标识读取，拿到同一笔数据。
- 同一幂等键重复提交，不产生第二笔数据，两次响应一致。
- 同一幂等键、不同正文，返回 409。
- 需要登录时，未认证请求返回 401，响应不含内部异常。
- 非法状态跳转（如重复取消）返回 409 且只生效一次。

## 测试金字塔

- 领域单测：状态机每条合法与非法跳转、幂等分支。数量最多，跑得最快。
- 接口契约测试：状态码、错误码、分页行为。
- 端到端：一条主路径（创建后读取）即可，不要在端到端层穷举分支。

测试数据各自构造、各自清理，不共享可变夹具；能并行跑的测试才是可维护的测试。

## 退回

写接口存在但没有幂等约定时，退回 API 角色一次。退回后仍没有，就把缺口记入 gaps 并继续，不做第二次退回。接口角色还没轮到时只起草验收测试，不退回。

## 自检

- 每条验收标准都有对应测试吗？
- 有没有只测成功路径的接口？失败路径至少要有参数错误和冲突。
- 测试失败时的报错信息能看出业务场景吗？
