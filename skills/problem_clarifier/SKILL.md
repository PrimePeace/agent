# 问题梳理

先回答四件事：谁在用、要完成什么动作、怎样算做完、哪些条件已经写明。缺了能执行的目标就停下来问，不要把猜测交给方案角色。

## 判断需求是否能执行

按顺序检查，缺一项就记一个具体问题：

1. 调用方：句中有「用户、管理员、运营、调用方」吗？没有就问「谁在用这个能力」。
2. 动作：有「创建、查询、取消、支付」这类动词吗？只有「做一个系统」不算动作。
3. 业务对象：有订单、商品、工单这类名词吗？调用方不是资源——「用户可以创建订单」里资源是订单。
4. 成功标准：能写出一条可判定对错的句子吗？「界面好看」不可判定，「创建后 1 秒内能按订单号查到」可判定。

前两项都缺时直接等待补充，并把缺的问题原样列给用户，一次问全，不要挤牙膏。

## 必须写进简报

- 用原文复述问题，点明业务对象和调用方。
- 约束只记录原文出现的峰值、延迟、一致性和范围。原文没写的放进假设并标明。常用默认假设：峰值未知按低于 2000 QPS；一致性未写按单库本地事务；身份未写按写接口需要认证。
- 验收标准至少包含：创建、按标识读取、写请求重复提交不产生第二笔数据。原文提到取消就加「取消可重复调用且只生效一次」；要求登录就加「未认证返回 401 且响应不含内部异常」。
- 盲区逐项标成已覆盖或未决。未决项写成一个具体问题，不要写「待定」。

## 默认要检查的盲区

| 盲区 | 要问的问题 |
| --- | --- |
| 身份与权限 | 谁能调用？未认证是拒绝还是允许匿名读？ |
| 幂等与重复提交 | 超时重试应返回同一结果，还是允许第二笔数据？ |
| 失败与补偿 | 下游失败时直接报错，还是先记录再补偿？ |
| 数据保留 | 数据保留多久？删除是物理删除还是标记删除？ |
| 可观测性 | 上线后靠哪些指标判断健康？ |
| 容量 | 峰值多少？超限时限流还是排队？ |
| 租户隔离 | 数据要按租户隔离吗？ |

## 反例

- 不要把「做一个电商系统」拆成几十个功能自己猜范围。问清第一个要上线的动作。
- 不要替用户发明约束，例如没人说高并发就不要写 10000 QPS。
- 退回重入时不再追问，用默认假设冻结范围，把余下疑问记进盲区。
